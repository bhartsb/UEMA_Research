UEMA research release • port feasibility • written November 4, 2026; file facts read at 5:44 PM PST

Can UEMA run on an iPhone or a Mac?

The setting. MIMo is a simulated infant body moved by the physics program MuJoCo. UEMA is the learning program that controls it; UEMA_Research holds the code and a saved model of 18,131,745 parameters (README.md line 27), trained on Windows 11 with a CUDA graphics card (line 123). Terms used below:

model step
One 50 ms model update: 5 physics steps of 10 ms (train_mimo.py line 1282).
token and encoder
Each model step, each sense's encoder turns its readings into one token of 192 numbers (encoder_registry.py line 33). The saved model encodes six senses (model_receipt.json): vision (camera images), tactile (skin pressure), audio (sound at the ears), proprioception (where each body part is and how fast it moves), motor (the command, as a token) and vestibular (which way gravity pulls on the head) (definitions: docs/H84_REACH_SOLUTION_VISUAL_2026-10-23.html line 80). README.md line 18 lists a seventh, intermind, with no encoder in the receipt.
forward model
A transformer (4 blocks, 8 heads, width 192) that reads the last 128 model steps' tokens (768: resolver.py line 245) and outputs the next model step's predicted tokens.
command
26 body handles × 9 numbers (position, rotation, radius, strength) sent to the body (README.md lines 19-20).
wellness channel
One term of wellness, the per-model-step sum that scores the body's state from its senses.
goal ring and planner
The goal ring stores the tokens of the last 200 model steps. The planner takes its highest-wellness entry as the goal and changes the command by gradient descent on the difference between predicted and goal tokens, forward-model weights fixed.
safetensors
The format of model.safetensors: an 8-byte length, a JSON header of each tensor's name, type, shape and byte range, then the raw numbers (read from the file today).
Metal, MPS, MLX Swift
Metal is Apple's GPU programming interface; MPS (Metal Performance Shaders) is torch's mps device, tensors on the Apple GPU; MLX Swift is the Swift interface of MLX, Apple's array library with run-time gradients (section 8).
Core ML, ExecuTorch
Core ML is Apple's framework that runs a model compiled to its own file format; ExecuTorch is PyTorch's runtime for a program exported ahead of time to a device (section 8).
jetsam
iOS ending an app to reclaim memory; reason per-process-limit: the app "crossed the resident memory limit imposed by the system on all apps" (section 8).

1 • Verdict

What is feasible now, what needs changes, what is blocked, and the sequence

  1. Feasible with 6 release files changed: the Python trainer on an Apple-silicon Mac's CPU (option 2): mujoco 3.3.0 and torch 2.6.0 ship macOS arm64 wheels (PyPI), and lem_model.py line 785 already selects the CPU without CUDA. Mac speed: unmeasured.
  2. Feasible with 17 release files changed: the same trainer on the Apple GPU through mps (option 1): one device line, ten autocast literals, nine float64 sites moved to the CPU, three switch checks rerun. Which operators mps lacks: unmeasured.
  3. Buildable, inference only, one body: one Swift package with macOS and iOS targets (options 5 and 3): MuJoCo from source, a Metal renderer, model and planner in MLX Swift. Unmeasured: whether Metal pixels give the OpenGL renderer's vision tokens; no Swift tactile sense exists.
  4. Blocked: training on an iPhone (option 4): no PyTorch runtime for iOS; ExecuTorch training is "experimental" and cannot save trained weights; eight-world training used 29.8 GB on Windows against a developer-measured 6,144 MB per app.
  5. No option continues the released run exactly: continuation_state.py line 217 refuses the saved CUDA random-number state on any other device, so every Mac run branches from model step 494,025 with different random draws.
  6. Sequence: option 2 first (fewest changes; it writes the reference file every Swift test reads), the Swift macOS target beside it, then the iOS target, then option 1; option 4 waits for the trigger in section 4.

3 • Five obstacles

Which line creates each obstacle, and which documented fact settles it?

(a) The CUDA kernels in lem/native_ops.py do not block a port

The file builds a C++ extension with #include <cuda.h> (line 85), links cuda.lib (lines 3225-3227) and compiles a kernel through NVRTC, CUDA's run-time compiler of kernel source text (line 3040 names nvrtc64_130_0.dll). Its only importers, replay_buffer.py line 282 and training_step.py lines 22-27, sit inside try/except and are not imported by train_mimo.py or lem_model.py; without the compiler each wrapper runs plain torch (lines 3145-3147, 3304, 3336-3338, 3347). Apple silicon has no CUDA driver, and no Metal replacement is needed. vision_kernels.py serves the Unreal tokenizer only; the bridge cuts vision patches in numpy (vision_adapter.py).

(b) Mixed precision and float64 on the Apple GPU

lem_model.py lines 798-800 set float32 and autocast off on any non-CUDA device. The live precision is bf16, 16-bit brain floating point under autocast over float32 weights (master_config.yaml line 281). Ten autocast calls that turn bf16 on pass the literal "cuda": lem_model.py lines 2665, 4763, 6810, 6877, 6929, 8303, 8310; heads_all_slot_path.py 514; motor_asked_change.py 471; vestibular_input_path.py 398 (proprio_token.py line 535 passes it to turn autocast off). torch 2.6.0's autocast_mode.py accepts bfloat16 on mps from macOS 14; with the "cuda" literal kept it prints "CUDA is not available. Disabling". The PyTorch MPS note: "The MPS backend does not support torch.float64". The float64 sites on the released path: lem_model.py 2533-2534; hand_response.py 67-68, 107, 117, 138; persistent_memory.py 344-368 (six buffers); self_state_integration.py 41; prediction_audit.py 388. hand_response.py is inside the code hash that admission_check compares (lines 18, 266), so editing it means rerunning that comparison.

(c) Eight processes and 29.8 GB against an iPhone app's memory

datasource.py line 495 uses spawn, which Python's documentation calls "The default on Windows and macOS"; it also states an iOS app "cannot use any form of subprocessing, multiprocessing, or inter-process communication". A one-world in-process source exists (train_mimo.py lines 1933-1934), but the saved episode resumes only with eight worlds (lines 1869, 1889-1890), and a fresh episode is allowed only with --eval-only (lines 1862-1864). Apple publishes no per-app number; one developer measured 6,144 MB on an iPhone 16 Pro Max with the increased-memory-limit entitlement. 29.8 GB is 5.0 times that; above the limit, jetsam ends the app. One world would hold a 400 MB arena and 73.1 MB of weights (7.7% of 6,144 MB); its total is unmeasured.

(d) Rendering the vision sense on macOS and iOS

MuJoCo's renderer "is written in C and uses OpenGL 1.5" (its documentation). On macOS the mujoco 3.3.0 package's gl_context.py (lines 31-32, 43-44) selects CGL, Apple's windowless OpenGL context, and since 2.3.4 "Offscreen rendering on macOS is no longer restricted to the main thread". The 3.3.1 changelog "Fixed a bug that caused shadow rendering to flicker on platforms (e.g., MacOS)"; the release pins 3.3.0. iOS has no OpenGL path: Apple lists OpenGL ES on "iOS: 2.0.0 - 12.0.0" only. An iOS app can read mjvScene, MuJoCo's list of shapes to draw, "independent of any graphics library", and draw it in Metal. The App Store app iMuJoCo states it runs MuJoCo on iPhone "with native Swift UI and Metal rendering" (source unpublished). Whether Metal pixels give OpenGL's vision tokens is unmeasured.

(e) No PyTorch on iOS: MLX Swift, Core ML and ExecuTorch

PyPI has no torch 2.6.0 wheel for iOS, and "PyTorch Mobile is no longer actively supported" (PyTorch iOS tutorial). Acting needs gradients: every 10 model steps once the goal ring holds 20 entries (lem_model.py line 4252; args.json line 62), the planner runs 21 forward-model evaluations and 20 backward passes (intention_generator.py lines 271, 300, 392-393), plus 20 Adam updates through the hand model (hand_response.py lines 161, 176). ExecuTorch needs iOS 17, deprecates its MPS backend "as of ExecuTorch 1.2", and its training README states "This feature is experimental", "We don't have a way yet to serialize the newly trained weights", optimizers "currently SGD and AdamW". Core ML gives no gradient with respect to an input ("can only update a compiled model file"), so it cannot run the planner. MLX Swift declares iOS 17, ships Adam and AdamW, computes gradients at run time, loads .safetensors, trains a small network on iOS in its MNISTTrainer example, builds only through Xcode, runs float64 "only with CPU operations", and cannot evaluate arrays on the iOS simulator. MLX Swift is the runtime that can run the planner on a phone.

Why training stays off the phone. Training is a backward pass every model step (lem_model.py line 4025), replay on 24 windows of 129 model steps every 2 model steps (args.json lines 57-58), the 3-pass imagination chain (args.json line 90; lem_model.py line 3121), AdamW's two running averages per parameter (optimizer.pt, 138.1 MB), the replay ring (replay.py line 64; 194.9 MB for eight bodies, computed from its tensor shapes) and the 489.3 MB runtime state.
